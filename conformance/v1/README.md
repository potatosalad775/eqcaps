# Engine conformance vectors

Test vectors for **engines**: implementations of SPEC §13. A port to another language is
conformant when it passes every vector here (SPEC §13.8). Format fixtures for profile validators
live in [`profiles/`](profiles/README.md). Everything here is CC0-1.0.

The files are generated by [`scripts/conformance.ts`](../../scripts/conformance.ts) (`npm run
conformance`) from hand-written inputs. The reference engine in `packages/core` supplies the
expected output of the exact ops. Don't edit them by hand: change the inputs in the script and
regenerate. A change to a vector is a change every port has to follow, so review the diff.
`npm run check` fails if a file is out of date.

## Files

One file per operation, named after it: `project.json`, `resolveSlot.json`, `toRealized.json`,
`toWritten.json`, `validate.json`, `assign.json`, `fit.json`, `complete.json`.

```jsonc
{
  "description": "What the operation is.",
  "vectors": [
    {
      "description": "What this vector shows.",
      "profile": "examples/b-jds-labs-element-iv",   // absent for project
      "op": "resolveSlot",
      "input": { "slot": 0 },
      "expect": { }
    }
  ]
}
```

`profile` is either:

- a path under `profiles/` without `.json`, such as `"examples/h-realization-laws"`, or
- an [RFC 7386](https://www.rfc-editor.org/rfc/rfc7386) merge patch over
  [`profiles/base.json`](profiles/base.json) (4 PK slots, stepped `q` and `gain`, no preamp). A
  `"$base"` key names another file under `profiles/` to patch instead. Merge patches can't set a
  value to `null`, so `"$base"` is how a vector patches an unbounded profile.

Some patched profiles deliberately carry what only a newer format minor would have, such as an
unknown rule type, to test lenient consumers (SPEC §15).

## Inputs and expectations

Filters are `{ "type", "freq", "q", "gain" }`, and `slots` arrays use `null` for an empty slot.

| `op` | `input` | `expect` |
| --- | --- | --- |
| `project` | `value`, `domain`, `field` (`freq` `q` `gain` `preamp`, or `type` with `domain` the slot's types) | the projected value |
| `resolveSlot` | `slot`, optional `filter` | the `EffectiveSlot` |
| `toRealized`, `toWritten` | `filter` | the filter |
| `validate` | `slots`, optional `preamp` | the `Violation[]`, in order |
| `assign` | `filters` | `{ "valid" }`: whether an assignment exists in which every active filter has a slot that accepts it as is |
| `fit` | `filters`, `preamp` | `{ "feasible" }` |
| `complete` | `slots` | `{ "warnings" }`: the `{ slot, code }` warnings, in slot order |

JSON has no NaN or infinities, so `project` inputs spell them `"NaN"`, `"Infinity"` and
`"-Infinity"`.

## Checking

- **Exact ops** (`project`, `resolveSlot`, `toRealized`, `toWritten`, `validate`): the output
  must equal `expect`. Numbers compare with the SPEC §4 tolerance, `|a − b| ≤ 1e-9 · max(1, |a|,
  |b|)`, and everything else exactly, object keys included.
- **Property ops**: the output isn't fixed. A runner checks the properties of SPEC §13.5–§13.7 on
  every vector, plus the facts in `expect`:
  - `assign`: inactive filters get no slot; if `valid`, every active filter gets a slot whose types
    and domains accept it.
  - `fit`: sound, safe, faithful, idempotent, and no added filters; `feasible` as given.
  - `complete`: exactly `bandCount` filters, filled slots unchanged, fillers in their domains and
    neutral unless warned, `ascendingFrequency` kept when `validate` found room; `warnings` as
    given.

The reference runner is
[`packages/core/test/conformance.test.ts`](../../packages/core/test/conformance.test.ts), with the
property checks in [`checks.ts`](../../packages/core/test/checks.ts) next to it. It also checks
that every op has vectors and that every violation code is produced by some `validate` vector.
